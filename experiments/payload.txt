# Performance Review: `llm_report_builder.py` & `weekly_dashboard.py`

Both scripts share a common architecture flaw that dominates everything else: **they materialize the entire matched content of a multi-gigabyte SQLite database in Python memory, then build an in-memory HTML string on top of it.** Everything else is secondary. Below is the full analysis, ranked by severity, with semantics-preserving rewrites.

---

## 1. Cost model (so we can rank findings)

Let:

- **N** = total rows in `responses`
- **C** = matching conversations
- **T** = total turns across matched conversations (T ≈ N in the worst case for a "U:"-heavy user)
- **B** = bytes of prompt/response/attachment payload per row (agent prompts with `<documents>` blobs are routinely 10–500 KB)
- **E** ≈ 1.05–6× B after `html.escape` (worst case 6×: `"` → `&quot;`)

Current report builder peak memory is roughly **S₁ (all first prompts, held by `fetchall` on the selection) + S₂ (all matched rows as dicts) + E (escaped HTML) + a transient copy of E from `"".join"`**. For a realistic agent DB (5,000 matched convs × 8 turns × 12 KB avg row): S₂ ≈ 480 MB, E ≈ 550 MB → **>1.5 GB RSS and swap death on a laptop**, all to produce a file whose visible content is first-prompt + last-response per conversation.

## 3. Deep dive & rewrites — `llm_report_builder.py`

### 3.1 The key structural insight

The page needs, per conversation: **first prompt, last response, and small metadata.** It never renders intermediate prompts/responses — they're only touched by (a) token sums, (b) model set, (c) the reasoning scan. So split into a **cheap metadata pass in SQL, then a per-conversation streaming pass**, and write the HTML incrementally. Peak memory drops from O(total content) to O(largest single conversation).

**Pass A — one aggregate query, ships only scalars:**

```python
def conv_headers(con, col_names, since_coarse=None):
    tok_cols = ("input_tokens" in col_names and "output_tokens" in col_names)
    tok_sql = ("SUM(COALESCE(input_tokens,0)), SUM(COALESCE(output_tokens,0)),"
               if tok_cols else "")
    since_sql = "AND substr(r1.datetime_utc,1,10) >= ?" if since_coarse else ""
    args = (since_coarse,) if since_coarse else ()
    q = f"""
        WITH agg AS (
            SELECT conversation_id, MIN(id) first_id, MAX(id) last_id,
                   COUNT(*) turns, {tok_sql} group_concat(DISTINCT model) models
            FROM responses GROUP BY conversation_id
        )
        SELECT a.conversation_id, a.first_id, a.last_id, a.turns,
               {tok_sql and "a.in_tok, a.out_tok,"} a.models,
               r1.datetime_utc AS first_dt, r2.datetime_utc AS last_dt,
               (COALESCE(instr(r2.response,'SUMMARY'),0) > 0
                AND COALESCE(instr(r2.response,'SUGGEST'),0) > 0) AS is_pass
        FROM agg
        JOIN responses r1 ON r1.id = a.first_id
        JOIN responses r2 ON r2.id = a.last_id
        WHERE r1.prompt GLOB 'U:*' {since_sql}
        ORDER BY a.first_id
    """
    return con.execute(q, args).fetchall()
```

Notes:

- `instr()` computes PASS/FAIL **inside SQLite** — no last-response text crosses the boundary for the grid, badges, or the stdout summary. `instr` is a case-sensitive substring search, byte-identical to `"SUMMARY" in resp`.
- `GLOB 'U:*'` already guarantees the prefix; drop the Python guard and drop `r.prompt` from the projection entirely (fixes P1/first-bullet: no more double fetch of first prompts, and no `fetchall` holding them).
- `group_concat(DISTINCT model)` skips NULLs just like the original `{r["model"] for r in rows if r.get("model")}`; re-split and `sorted()` in Python. (Caveat: model IDs containing commas would corrupt the split — llm model IDs don't contain commas; add a comment.)
- **Honest I/O caveat:** `SUM(input_tokens)` still forces SQLite to *traverse* each row's record, and because `input_tokens`/`output_tokens` sit **after** `prompt` and `response` in llm's schema, reaching them means walking the overflow-page chains of the big columns. Page I/O is therefore near-identical to `SELECT *`; what you save is the **UTF-8 decode (~0.5–1 GB/s of pure CPU), millions of temporary Python string objects, and all retention**. That's still the dominant win on wall-clock and RSS.

**Pass B — per-conversation streaming render:**

`render_card` fetches the conversation's rows, keeps only what it needs (first prompt HTML, last response HTML, reasoning entries), and lets the rest be garbage-collected before the next conversation. The grid/status/summary all come from Pass A, so no pre-pass over content is needed. `is_pass` from SQL replaces all three redundant `pass_fail` recomputations (P2).

The `--since` coarse+exact split is semantics-preserving: the SQL prefilter uses `cutoff − 1 day` (a stored datetime with a non-UTC offset can lag UTC by at most a day), then the *identical* Python expression from the old code runs as the exact filter. Offsets near midnight, NULLs, and unparseable values all behave exactly as before.

### 3.2 `collect_reasoning`: prefilter + early exit, keep the two-pass order

The 25-entry cap interacts with ordering: all name-column hits precede all JSON hits. Preserving that order requires two passes — but the rows of a *single* conversation are bounded, so keep them in memory for the conv only, and add two cheap guards:

```python
SPELL = re.compile(r"reason|think", re.I)   # raw-text prefilter

def collect_reasoning(rows, col_names, cap=25):
    lines, seen = [], set()
    name_cols = [c for c in col_names if REASON_RE.search(c)]
    # pass 1: matched column names
    for row in rows:
        for c in name_cols:
            v = row.get(c)
            if v is None or (isinstance(v, str) and not v.strip()):
                continue
            sv = display_value(v)
            if (c, sv) not in seen:
                seen.add((c, sv)); lines.append((c, sv))
    if len(lines) >= cap:
        return lines[:cap]                      # pass 2 cannot change the first cap
    # pass 2: JSON scan — parse only when a match is even possible
    for row in rows:
        for c in col_names:
            v = row.get(c)
            if not isinstance(v, str):
                continue
            s = v.lstrip()                       # returns self if nothing stripped (CPython)
            if not s or s[0] not in "{[":
                continue
            if not SPELL.search(v):              # C-level scan, no allocation
                continue                         # no key can match → skip json.loads
            try:
                data = json.loads(v)
            except Exception:
                continue
            if isinstance(data, (dict, list)):
                out = []
                _deep_reason(data, c, out)
                for p, val in out:
                    sv = display_value(val)
                    if (p, sv) not in seen:
                        seen.add((p, sv)); lines.append((p, sv))
                        if len(lines) >= cap:
                            return lines
    return lines[:cap]
```

The prefilter is sound: `REASON_RE` only ever matches *parsed keys* whose text contains ASCII `reason`/`think`, and a JSON key containing those letters forces the same substring into the serialized source (ASCII letters are never mandatorily escaped). The one theoretical escape hatch is a producer emitting `\u0072eason`-style escapes for plain ASCII — vanishingly rare; if you need bit-exact parity, gate the prefilter behind a flag. For a DB where 5,000 conversations each carry a 200 KB `attachments` JSON with no reasoning keys, this alone removes ~1 GB of `json.loads` work.

**Advanced option (mention, don't mandate):** if SQLite is built with JSON1, the whole pass-2 can be pushed down (`json_tree(r.attachments)` with `instr(r.attachments,'reason')>0 OR instr(r.attachments,'think')>0` as the gate), keeping parse CPU in C and shipping only truncated values. `display_value`'s exact formatting (`ensure_ascii=False`, `\r`→space) is harder to reproduce exactly, so I'd only take this after the diff-based acceptance test below.

### 3.3 Share the doc-span computation (P2)

`render_first_prompt` currently runs all five `find_doc_spans` regexes **twice** per prompt:

```python

```

I deliberately did **not** merge the five patterns into one alternation. The current code unions *overlapping* matches from independent patterns (which correctly handles malformed nesting like `<document><source>a</document>b</source>`); a single alternation consumes the first match and can miss an overlapping match that extends past it. Keep 5 `finditer`s, run them once — 5 scans instead of 10, zero behavioral risk.

## 4. Deep dive & rewrites — `weekly_dashboard.py`

### 4.1 Fix the variable-limit bug and the planner landmine in one move

Chunk the `IN` list **and** stop asking for a global `ORDER BY id` over fat rows. The dashboard needs: per conv — turns, first datetime, first model, last response snippet, token sums; plus a global model histogram. None of that needs intermediate prompts or responses:

```python

            for m, cnt in con.execute(

                f" WHERE conversation_id IN ({ph}) GROUP BY model", chunk):
                hist[m or ""] = hist.get(m or "", 0) + cnt

            for cid, dt, model, resp in con.execute(
```

This eliminates: the >999 crash, the full-table-scan-or-external-sort planner coin flip, all intermediate `SELECT *` payloads (the week's entire prompt corpus), and the retention of `rows` through `build_html` (compute `in_tok`/`out_tok`/models from `meta`+`hist` and pass those instead).

Same honest caveat as §3.1 applies to the token SUMs (column order forces overflow-chain traversal server-side); the model histogram is the one query that's *actually* cheap end-to-end because `model` precedes the payload columns.

### 4.2 Snippet: anchor, slice, then normalize

```python
WS_RUN = re.compile(r"\s+")

def snippet(resp, limit=220, window=800):
    if not resp:
        return ""
    m = FIRST_NS.search(resp)                  # C-level skip of leading whitespace
    s = resp[m.start():m.start() + window] if m else ""
    s = WS_RUN.sub(" ", s).strip()

```

Regex over ≤800 chars instead of the full response. Divergence from the original is confined to pathological inputs (e.g., a >580-char whitespace run inside the first 800 chars truncating the snippet early) — document it, or widen `window` if that bothers you.

| Dimension | Current (report builder) | After |
|---|---|---|
| Content bytes shipped to Python | O(T·B) — every row, every column | O(C·(first prompt + last response)) + per-conv streamed rows for reasoning |
| Peak RSS | ≈ S₁ + S₂ + ~2E (GBs on an agent DB) | ≈ largest single conversation + output buffer |
| Last-response scans for status | 3 per conv, in Python | 0 (SQL `instr`, reused for grid+cards+summary) |
| First prompts fetched | 2× (selection + refetch), all retained | 1×, only during that conv's card render |
| `--since` | post-fetch (all filtered work wasted) | coarse SQL pushdown + exact Python filter |
| Reasoning scan | 2 passes, parses every JSON payload, no cap exit | 2 passes (order-preserving), prefiltered parses, early exit |
| Doc-span regex | 10 scans/prompt | 5 scans/prompt |
| Dashboard SQL | crash >999 convs; full scan or external sort | chunked; index-ordered; endpoint fetch only |
| Dashboard memory | whole week's rows alive until file written | O(1) per conversation + histograms |

## 6. Verification plan (acceptance gate)

1. **Semantics:** run old and new on the same real DB; `diff` the HTML outputs must be byte-identical (modulo the two documented micro-divergences: snippet whitespace-run edge, `\u`-escaped-ASCII reasoning keys).
2. **Plans:** `EXPLAIN QUERY PLAN` each new query; assert no `USE TEMP B-TREE FOR ORDER BY` on the big queries and covering-index usage for the GROUP BY.
3. **Scale:** `/usr/bin/time -v` + `tracemalloc` on the largest available `logs.db`; target RSS < ~100 MB regardless of DB size, and wall-time dominated by the single aggregate pass.
4. **Limits:** synthesize ≥1,000 matching conversations to prove the dashboard no longer hits the bind-parameter ceiling.

## 7. Deliberately left alone

- `html.escape` cost and final HTML size — inherent, since the full text is intentionally embedded in `<details>`; the 6× worst-case expansion is a property of the content.
- The N+1 per-conversation loop (statement cache + index probes make it negligible next to content I/O).
- Parallel rendering — the bottleneck is single-connection SQLite page reads; sharding read-only connections across processes adds complexity for little gain since the OS page cache is already shared.
- Compression/external assets — excluded by the self-contained, no-network requirement.
